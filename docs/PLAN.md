# План реализации `ebay_orders`

Главная спецификация — `docs/SPEC.yaml`. Этот документ её **не дублирует**: только
последовательность работ, что входит и что НЕ входит в каждый этап, какую
терминальную проверку и какую Exa-документацию надо пройти **перед** написанием
кода. Ссылки `[[id]]` — на definitions/steps в SPEC.yaml.

Принципы из `CLAUDE.md`, по которым строится план:
- никаких фолбеков и overengineering (нет «второй модели на всякий случай»,
  нет «дублирующего валидатора в Python», нет лишних tools);
- перед реализацией читаем актуальные доки подсистемы и щупаем поведение в
  терминале на живом окружении (Postgres, FastAPI, OpenRouter);
- если терминал показал, что предположение было неверным, сначала
  корректируем понимание, потом продолжаем;
- после каждого шага прогоняем не только unit, но и реальные сценарии и
  edge-cases в терминале;
- то, что договорено в чате, но не отражено в SPEC.yaml, лежит здесь.

Перед стартом каждого этапа обязательно:
1. **Обсудить детали с пользователем.** Закрыть открытые вопросы этапа.
2. **Углубить ресёрч через Exa** именно по подсистемам этапа.
3. **Проверить руками в терминале** ключевые механики, на которые опирается
   код этапа: сначала команда в shell/psql, потом строка кода.
4. После реализации — пройти живые сценарии и edge-cases в терминале, а не
   только unit-тесты.

## Зафиксированные решения (после обсуждения и живой проверки)

| Решение | Значение | Чем подтверждено |
|---|---|---|
| Стек бэкенда | FastAPI **0.136.1** (Python 3.14.3) + `asyncpg` 0.31.0 + один процесс с двумя пулами воркеров (A и B) | PyPI/GitHub release pages, asyncpg supports PG 9.5–18 |
| Стек фронта | Next.js **16.2.4** + AI SDK **6.0.175** (`ai` + `@ai-sdk/react`) + `useChat` multimodal parts | npm latest, vercel/next.js latest |
| OCR-модель (стадия A) | `moonshotai/kimi-k2.6` через OpenRouter, structured outputs `response_format: json_schema, strict: true` | OpenRouter docs, релиз 20 апр 2026, мультимодальная, 262K контекст |
| Модель агента (стадия B) | `moonshotai/kimi-k2.6` через OpenRouter с tools (`save_order_details`, `sql_read`, `delete_order`) | та же модель, нативный tool-use |
| Без авто-фолбека | Если стадия A или B падает — ошибка пользователю, без попытки другой моделью | [[Стадия A распознавание одного снимка#ошибка]] и `CLAUDE.md` |
| Postgres | 18.3 на `2.26.53.128:5405`, БД `ebay_orders`, роль `admin`, пароль через `POSTGRES_PASSWORD` | живой `SELECT version()` |
| `postgres_fdw` | НЕ ставим. Все слои в одной БД, FDW нужен только для другой Postgres-инстанции | YAML, проверено через docs PG 18 F.38 |
| Валидация | Жёсткие правила — на стороне Postgres: `CHECK`, доменные типы, `UNIQUE`, `FOREIGN KEY`, `CREATE CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` для кросс-табличных инвариантов. В Python — только то, что нельзя выразить SQL | живая проверка DEFERRABLE-триггера, см. `appendix A` ниже |
| Инструменты агента | Ровно три по SPEC.yaml: `save_order_details`, `sql_read`, `delete_order`. Никаких `link_screenshot` / `mark_unlinked` (их в YAML нет). Связи с снимками пишет сам `save_order_details` | [[инструмент сохранения заказа#запись]] |
| `order_change_log` | Пишет триггер `AFTER INSERT/UPDATE` на `orders / order_items / order_refunds`, не Python | [[чистовые таблицы]], CLAUDE «один источник правды» |
| Очередь стадий | `SELECT … FOR UPDATE SKIP LOCKED` по `screenshots` с partial-индексами на `ocr_status='pending'` и `agent_status='pending'`. Без Redis/Celery | подтверждённый паттерн PG 18, статья Cybertec и Asghar Kaleji |
| Round-trip | измерено живьём: ~85–120 мс на `SELECT 1`. Один save = одна транзакция, по возможности один round-trip с CTE `WITH … RETURNING`. Воркеры держат персистентный пул `asyncpg.create_pool` | живой psql `\timing` |
| Тестирование | Первично — терминальные сценарии (psql, curl, прогон A на `last_photos/` с печатью «вот что модель видит»). pytest — только для нормализации дат/денег | ответ пользователя |
| `session_id` | UUID на открытие страницы, без localStorage | [[чат и сессия#session-id]] |

`postgres_fdw` (он же часто пишется `postgresfwd`) нужен ровно для одной задачи —
ходить из одной Postgres-базы в **другую** Postgres (`CREATE SERVER` +
`CREATE FOREIGN TABLE`, см. PG 18 docs F.38). У нас одна база, все слои в ней,
поэтому FDW сейчас — это лишний модуль и оверинжиниринг по `CLAUDE.md`. Если
позже появится отдельная аналитическая Postgres — добавим миграцией.

## Этап 1 — Фундамент данных и Postgres-валидация

Цель: чтобы ни одна противоречивая запись физически не могла попасть в БД.
Жёсткая валидация — через SQL, не через Python.

### Что входит

- **Подключение и базовое окружение.** Файл `.env` с `POSTGRES_PASSWORD`,
  `OPENROUTER_API_KEY`. Скрипт `scripts/db.sh` — обёртка над psql с
  правильными хостом/портом/юзером, чтобы дальше не повторять.
- **Расширения:** `CREATE EXTENSION pg_trgm` (нечёткий поиск по `sold_by`,
  `item_title` для [[ИИ проверка совпадения]] и [[правила группировки снимков]]),
  `CREATE EXTENSION pgcrypto` (на всякий — `gen_random_uuid()` для
  `chat_sessions.id`).
- **Доменные типы:**
  - `money_usd_nonneg` = `numeric(12,2)` `CHECK (VALUE >= 0)`;
  - `sha256_hex` = `char(64)` `CHECK (VALUE ~ '^[0-9a-f]{64}$')`;
  - enum `ocr_status_t` и `agent_status_t` со значениями из
    [[статусы обработки]] (`pending|running|done|failed`).
- **Технический слой по [[технические таблицы]]:** `screenshots`, `raw_ocr`,
  `chat_sessions`, `chat_messages`. PK `screenshots.sha256` гарантирует
  «повторная загрузка не создаёт дубль» из [[технические таблицы#screenshots]].
- **Чистовой слой по [[чистовые таблицы]]:** `orders` (поля по
  [[поля идентификации заказа]] + [[денежные поля заказа]] + [[поля доставки заказа]] +
  `created_at`, `updated_at`, `deleted_at`, `deleted_reason`),
  `order_items`, `order_refunds`, `order_screenshot_links`, `order_change_log`.
- **Жёсткие SQL-инварианты:**
  - `NOT NULL`/`UNIQUE`/`FK` по обязательным полям;
  - `CHECK`: `delivered_date IS NULL OR delivery_status IS NOT NULL`,
    `is_untracked = false OR cardinality(tracking_numbers)=0`,
    `tracking_numbers` уникальны внутри строки;
  - `CHECK` на удаление: `(deleted_at IS NULL) = (deleted_reason IS NULL)`
    (см. [[инструмент мягкого удаления заказа#контракт]]);
  - **CONSTRAINT TRIGGER `DEFERRABLE INITIALLY DEFERRED`** на `orders` и
    `order_items` для проверки [[правила проверки сумм#формула]] и
    [[правила проверки сумм#строки-товаров]] в момент `COMMIT`. Поведение
    подтверждено живым тестом (см. `appendix A`).
  - **триггер `AFTER INSERT/UPDATE`** на `orders / order_items / order_refunds`
    пишет [[чистовые таблицы]]`.order_change_log` без участия Python.
- **Очередь:** partial-индексы
  `CREATE INDEX … ON screenshots (sha256) WHERE ocr_status = 'pending'`
  и `… WHERE agent_status = 'pending'` под паттерн
  `SELECT … FOR UPDATE SKIP LOCKED`.
- **Миграции:** одна базовая `migrations/0001_init.sql`, накатывается просто
  через `psql -f`. Без Alembic/Prisma — сейчас это лишняя сущность.
- **Терминальный smoke-тест `tests/sql/smoke.sh`.** Скрипт пытается обойти
  каждый CHECK и каждый CONSTRAINT TRIGGER:
  - вставить `money_usd_nonneg` со значением -1.00 → ошибка;
  - вставить `sha256` неправильной длины/символов → ошибка;
  - сделать `deleted_at IS NOT NULL AND deleted_reason IS NULL` → ошибка;
  - вставить `orders` с `item_subtotal_usd=100`, потом `order_items`
    суммой 90 → COMMIT обязан упасть с понятным сообщением;
  - вставить `screenshots` с одинаковым `sha256` дважды → второй
    `INSERT … ON CONFLICT DO NOTHING` не создаёт дубль.

### Что НЕ входит в Этап 1

- Никакого Python-кода и никакого FastAPI.
- Никакого OCR, никаких воркеров стадий A/B.
- Никакого фронта, чата, AI SDK.
- Никаких бизнес-валидаторов в коде приложения, дублирующих CHECK.
- Никакого `postgres_fdw`, никакой репликации, никакой read-only роли.
- Никакого pgvector/RAG-индекса (в SPEC.yaml не упомянуто).
- Никаких Alembic/Prisma миграций.

### Что нужно изучить через Exa перед стартом Этапа 1

- PG 18 docs: `CREATE TABLE`, `CHECK`, `CREATE DOMAIN`, `CREATE TRIGGER`,
  `CREATE CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED`.
- `pg_trgm` (similarity, GIN-индекс по `item_title` и `sold_by`).
- `FOR UPDATE SKIP LOCKED` + partial index pattern (для готовности к Этапу 2).
- Cybertec/Vlad Mihalcea про триггер-инварианты с MVCC и race conditions.

### Что проверить в терминале до кода Этапа 1 (часть уже сделана, см. appendix A)

- Латентность одного round-trip от dev-машины — сделано (~100 мс).
- `DEFERRABLE` поведение — сделано (триггер срабатывает на COMMIT).
- Доступность расширений — сделано (`pg_trgm`, `pgcrypto`, `citext`,
  `postgres_fdw` все в `pg_available_extensions`, `plpgsql` установлен).
- Параллельный SKIP LOCKED-тест: запустить два psql одновременно, чтобы
  убедиться, что второй не блокируется.
- Прогнать `0001_init.sql` на тестовой БД (или локальном Docker Postgres 18) —
  убедиться, что все DDL применяются и smoke-скрипт зелёный.

### Критерий завершения Этапа 1

- Миграция накатывается на пустую `ebay_orders` без ошибок.
- `tests/sql/smoke.sh` проходит: каждый запрещённый случай возвращает
  SQL-ошибку с понятным сообщением, каждый разрешённый коммитится.
- Латентность одного `INSERT INTO orders … RETURNING …` в сети ≤ 200 мс
  на персистентном коннекте.

## Этап 2 — Стадия A: распознавание одного снимка

Цель: «глаза» системы. На вход один файл, на выход одна валидная запись
`raw_ocr` или явная ошибка. См. [[Стадия A распознавание одного снимка]] и
[[формат сырого распознавания]]. Параллельно — минимальный приём файлов,
чтобы было что подавать на стадию A.

### Что входит

- **FastAPI-бэкенд (один процесс).** Конфиг через `pydantic-settings`,
  персистентный пул `asyncpg.create_pool(min_size=2, max_size=10)`.
  Внутри процесса — два пула воркеров: стадия A и **заглушка** B
  (на этом этапе только переводит снимок в `agent_status='done'` без
  реальной обработки, чтобы не блокировать поток; реальная B — Этап 3).
- **Endpoint приёма файлов** `POST /api/upload` (или интегрированный с
  `/api/chat` — решим на обсуждении). Принимает multipart, считает `sha256`
  каждого файла, делает `INSERT INTO screenshots (…) ON CONFLICT (sha256)
  DO NOTHING`. Возвращает список `sha256` + признак «новый/уже был».
- **Воркер стадии A.** Один цикл:
  1. атомарно захватывает один pending-снимок через `UPDATE … WHERE id IN
     (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING sha256, bytes`;
  2. кодирует `bytes` в base64, вызывает OpenRouter
     `moonshotai/kimi-k2.6` через OpenAI-совместимый клиент с
     `messages=[{ role:'user', content:[{type:'image_url', …},
     {type:'text', text: <prompt>}] }]` и
     `response_format: { type:'json_schema', json_schema: { strict:true,
     schema: <по [[формат сырого распознавания]]> } }`;
  3. валидирует ответ против JSON-схемы Pydantic (`raw_ocr.schema_version`);
  4. на успех — `INSERT INTO raw_ocr (…)`, `UPDATE screenshots SET
     ocr_status='done'` в одной транзакции;
  5. на провал — `UPDATE screenshots SET ocr_status='failed',
     error_text=…` ([[Стадия A распознавание одного снимка#ошибка]]).
     Никаких авто-повторов другой моделью.
- **CLI-скрипт `scripts/run_stage_a.py <path>`** — прогоняет один файл
  через стадию A без HTTP-обёртки и **печатает** распознанное
  («вот что модель видит»: `is_order_details`, все непустые `observed.*`,
  `unreadable[]`). Это и есть терминальный тест по просьбе пользователя.
- **Минимальный фронт-стенд.** Либо curl-сценарий, либо черновой
  Next.js + AI SDK с одной кнопкой загрузки. Полноценный чат и стрим
  ответа — Этап 3.
- **Терминальные сценарии:**
  - прогон `scripts/run_stage_a.py` по 10–20 файлам из `last_photos/` с
    печатью увиденного — оценить, какие поля стабильно вытаскиваются и
    какие надо чинить промптом;
  - проверка идемпотентности: повторная загрузка того же файла не даёт
    дубль в `screenshots` и не запускает повторный OCR;
  - проверка падения: подсунуть HTML-картинку (не Order details) —
    `is_order_details=false`, снимок завершается `ocr_status='done'`
    (а в ошибку группы он попадёт только на Этапе 3).

### Что НЕ входит в Этап 2

- **Стадия B, агент**, инструменты `save_order_details`, `sql_read`,
  `delete_order` — не реализуем.
- **Никаких бизнес-правил:** ни группировки [[правила группировки снимков]],
  ни денежных правил [[правила денег USD]], ни сверки с базой
  [[правила конфликта с базой]].
- **Никаких чистовых записей** в `orders / order_items / order_refunds`.
  В `raw_ocr` — да, но это сырой слой.
- **Полноценный чат-UI с прогрессом и сводкой** — Этап 3.
- Никакого «второго OCR», никакого «попробовать другой моделью».
- Никакого хранения файлов вне Postgres (всё `bytea` в `screenshots`).
- Никаких pydantic-«валидаторов»-дублей того, что уже стоит CHECK-ом в БД.

### Что нужно изучить через Exa перед стартом Этапа 2

- **OpenRouter docs:** multimodal (`image_url` content type),
  structured outputs (`response_format.json_schema.strict=true`),
  страница `moonshotai/kimi-k2.6` — лимиты и параметры.
- **OpenAI Python SDK** (последний) с `base_url='https://openrouter.ai/api/v1'` —
  ровно так и работает с OpenRouter.
- **AI SDK v6:** `useChat` multimodal parts, `DefaultChatTransport`, передача
  файлов как data URL — на Этапе 2 ещё не нужно полноценно, но надо
  понимать форму, чтобы не переписывать на Этапе 3.
- `vercel-labs/ai-sdk-preview-python-streaming` — референс FastAPI + Data
  Stream Protocol.
- `asyncpg` 0.31 + bytea: bind-параметры, размеры (на наших файлах
  ~1 МБ — норма), `executemany` vs `UNNEST`.

### Что проверить в терминале до кода Этапа 2

- **OPENROUTER_API_KEY должен лежать в env.** На момент написания плана
  его в окружении нет.
- Один curl на OpenRouter с реальным base64 одного файла из `last_photos/`
  и jsonschema из [[формат сырого распознавания]] — посмотреть формат ответа
  K2.6, латентность, стабильность `is_order_details`.
- `time` обёртка: 5 параллельных запросов K2.6 — посмотреть rate limits.
- Через psql вручную: `INSERT INTO screenshots(bytes) … RETURNING octet_length(bytes)` на одном
  из `last_photos/*.png` (≈900 КБ) — убедиться, что bytea-инсерт через
  asyncpg по латентности укладывается во что-то разумное (target ≤ 300 мс).

### Критерий завершения Этапа 2

- На пачке 10–20 файлов из `last_photos/` стадия A проходит без падений
  бэкенда: на каждый снимок ровно одна строка в `raw_ocr` или ровно
  одна запись об ошибке. Повторная загрузка дублей не создаёт.
- `scripts/run_stage_a.py` печатает по каждому файлу читаемую сводку
  «вот что модель видит» — это и материал для проверки качества промпта,
  и видимое подтверждение работы.

## Этап 3 — Стадия B: агент, чистовой слой, чат-UI

Цель: «мозг и руки». Стадия B берёт готовые `raw_ocr`, собирает заказы,
проверяет правила, пишет чистовой слой, отвечает пользователю. См.
[[Стадия B сборка заказа]] и шаги
`захват-сессии-для-b → отправка-и-сохранение-ответа` в SPEC.yaml.

### Что входит

- **Полноценный чат-UI** на Next.js 16 + AI SDK v6 `useChat` + `DefaultChatTransport`,
  drag&drop файлов и папок, одна страница. `session_id` через
  `crypto.randomUUID()` ([[чат и сессия#session-id]]), без localStorage.
- **Серверный stream-handler** на FastAPI говорит по AI SDK Data Stream
  Protocol: `data parts` с прогрессом по [[ответ пользователю#прогресс]]
  и финальная сводка по [[ответ пользователю#сводка]] как обычное сообщение
  ассистента.
- **Воркер стадии B.** Один проход на пачку готовых `raw_ocr` текущей
  чат-сессии:
  - чтение [[формат сырого распознавания]] по новым `sha256`;
  - проверка [[поддерживаемая страница заказа]];
  - группировка по [[правила группировки снимков]] (без опоры на порядок
    файлов и имя файла);
  - объединение полей по [[правила объединения полей]];
  - проверка [[правила достаточности данных]];
  - проверка [[правила денег USD]] и [[правила проверки сумм]] (часть уже
    стоит в БД из Этапа 1; здесь — то, что нельзя выразить в CHECK,
    например «другая валюта без USD-эквивалента»);
  - сверка с базой через [[инструмент чтения базы]] и
    [[механическая проверка конфликта]];
  - **смысловая** [[ИИ проверка совпадения]] вызовом K2.6 — только если
    механика не нашла жёсткого конфликта;
  - [[финальная проверка перед сохранением]];
  - вызов `save_order_details` атомарно в одной транзакции
    ([[инструмент сохранения заказа#запись]]).
- **Инструменты агента (ровно по SPEC.yaml):**
  - `save_order_details` — единственный путь записи чистового слоя;
  - `sql_read` — общий SQL-read tool по [[инструмент чтения базы]] (только
    `SELECT`, через отдельный read-only коннект или явную проверку
    парсером, чтобы LLM физически не мог послать `UPDATE/DELETE`);
  - `delete_order` — мягкое удаление по
    [[инструмент мягкого удаления заказа#контракт]].
- **Текстовые сообщения без файлов:** ветка
  `обработка-текстового-сообщения → выбор-текстового-действия` —
  вопрос по данным, явная правка, мягкое удаление, или вопрос/ошибка
  по тексту.
- **Ответы пользователю:** только итог / прямой ответ / ошибка с причиной;
  внутренний JSON в чат не уходит ([[базовые правила#тихий-чат]]).
- **Терминальные сценарии:**
  - один заказ из одного снимка — happy path;
  - один заказ из 3–5 снимков (разные части одного заказа) → одна запись
    в `orders` + правильные `order_items`, `tracking_numbers[]`,
    `refunds[]`;
  - снимок-«пустышка» (страница товара) → [[ошибка-неподдержанной-страницы]];
  - снимок без `order_number`, который однозначно цепляется к одному
    сохранённому заказу → дозапись (но без перетирания заполненных полей);
  - тот же снимок, который подходит к двум заказам → [[ошибка-группировки]];
  - сумма в EUR без USD-эквивалента → [[ошибка-валюты]];
  - конфликт по `order_number` (другая сумма) → старая запись не
    переписывается, в чат — текст ошибки;
  - явная правка `«в заказе 12345 поменяй sales_tax_usd на 4.20»`
    → `save_order_details` с `source='user_chat'`;
  - явный запрос `«удали заказ 12345»` → `delete_order`,
    `order_change_log` записан триггером.
  - вопрос по сохранённому заказу → агент ходит через `sql_read` и
    отвечает текстом, без записи.

### Что НЕ входит в Этап 3

- Никаких новых инструментов сверх трёх.
- Никакого автоматического второго прохода LLM при провале первого.
- Никакого сохранения полей из [[поля которые не сохраняются]]
  (`currency`, `payment_*`, адреса, `carrier`, `page_type` и т.п.) —
  `save_order_details` физически не принимает такие ключи, а LLM-промпт
  явно перечисляет что нельзя.
- Никакой страницы списка заказов / админки. Один экран — чат.
- Никакого RAG / векторного поиска. Сверка с базой — обычный SQL +
  одно LLM-сравнение по похожим кандидатам.
- Никакой авторизации, ролей, мульти-юзера.
- Никакого экспорта CSV / интеграций — вне SPEC.yaml.

### Что нужно изучить через Exa перед стартом Этапа 3

- **AI SDK v6:** `createUIMessageStream`, `writer.write({type:'data-…'})`,
  `transient` parts, `onData` callback, multimodal `parts` в `useChat`.
- **AI SDK + Python:** UI Message Stream Protocol — нужная разметка
  SSE-чанков, чтобы Next.js `useChat` корректно парсил поток от FastAPI.
- Шаблоны tool-loop: модель внутри одного запроса делает несколько tool
  calls + структурированный финальный ответ.
- Postgres: `LISTEN/NOTIFY` или просто polling между стадиями A и B —
  выбираем при обсуждении.
- `pg_trgm.similarity()` — для нечёткого `sold_by` и `item_title` внутри
  [[ИИ проверка совпадения]].

### Что проверить в терминале до кода Этапа 3

- Минимальный FastAPI-роут пишет 2–3 data parts по AI SDK Data Stream
  Protocol — curl показывает корректные SSE-чанки, demo-`useChat` их
  принимает.
- На реальной базе после Этапов 1 и 2: psql-запрос «найди кандидатов по
  `order_number` ИЛИ `pg_trgm.similarity(sold_by) > 0.4`» — проверить
  индексы и план (`EXPLAIN ANALYZE`).
- Имитация tool-loop вручную: один curl на K2.6 с собранным контекстом
  и описанием трёх tools — убедиться, что модель действительно вызывает
  `save_order_details` с допустимыми полями и не пытается передавать
  поля из [[поля которые не сохраняются]].

### Критерий завершения Этапа 3

- Каждый из терминальных сценариев выше отрабатывает корректно: либо
  чистовая запись в `orders/order_items/order_refunds` без нарушения
  CHECK/CONSTRAINT TRIGGER из Этапа 1, либо у пользователя в чате —
  явная ошибка с причиной по [[ответ пользователю#ошибка]], без
  внутреннего JSON.
- Любая попытка обойти [[поля которые не сохраняются]] завершается
  ошибкой `save_order_details` или явным отказом агента — не молча.

## Appendix A — что уже проверено вживую (на момент написания плана)

```
$ psql -h 2.26.53.128 -p 5405 -U admin -d ebay_orders -c "SELECT version();"
PostgreSQL 18.3 (Debian 18.3-1.pgdg13+1) on x86_64-pc-linux-gnu, 64-bit
```

- public-схема пуста: `count(*) FROM information_schema.tables WHERE
  table_schema='public' = 0`.
- Доступные расширения (не установлены): `pg_trgm 1.6`, `pgcrypto 1.4`,
  `citext 1.8`, `postgres_fdw 1.2`. Установлен `plpgsql 1.0`.
- Round-trip `SELECT 1` на персистентном psql-сеансе: ~85–120 мс.
  Серверный цикл из 50 `PERFORM 1` = 0.5 мс. Вывод: воркеры **обязаны**
  держать персистентный пул, а save должен быть один round-trip с CTE.
- DEFERRABLE CONSTRAINT TRIGGER подтверждён живьём:
  - валидный кейс: `INSERT order(total=100); INSERT items(60,40); COMMIT;`
    — коммит проходит, хотя посередине транзакции инвариант нарушался;
  - невалидный: `INSERT order(total=50); INSERT items(30); COMMIT;`
    — `ERROR: sum(items) <> orders.total` ровно на COMMIT, заказ не
    появляется в таблице.
- Локально доступно: `psql 18.3` (Homebrew), Python 3.14.3, Node 24.14.0,
  pnpm 10.32.1.

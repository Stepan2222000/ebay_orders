# Заметки по работе с LLM-провайдером

Это не часть `SPEC.yaml` и не часть `PLAN.md`. Это сжатый опыт от живых
прогонов через LLM в этой системе. Сюда уходит то, что важно знать перед
тем как писать код, чтобы не наступать на те же грабли.

> **Этот файл заменяет прежние заметки про OpenRouter.** Блоки
> `<!-- ^технически -->` в `SPEC.yaml` (стадии A и B) описывают
> исторический OpenRouter-сетап (Kimi, `provider`-routing,
> `reasoning.effort`) и считаются устаревшими — фактический транспорт
> описан здесь.

## Что используем

Обе стадии ходят через **собственный OpenAI-совместимый прокси**
(`OPENAI_BASE_URL`, по умолчанию `http://2.27.20.221:8317/v1`), через
официальный пакет `openai` (`AsyncOpenAI`). API локальный/бесплатный —
**цены не считаем и не храним** (`usage.cost` прокси не отдаёт).

- **Стадия A** ([[Стадия A распознавание одного снимка]]) —
  `cursor-gpt55(low)` (`settings.ocr_model`). Vision: смотрит на один
  скриншот и отдаёт строго структурированный JSON по нашей схеме
  (`response_format: json_schema, strict: true` работает).
- **Стадия B** ([[Стадия B сборка заказа]]) — `cursor-gpt55(high)`
  (`settings.agent_model`) в режиме tool-calling: разговор с
  пользователем плюс [[инструмент сохранения заказа]] и [[инструмент SQL]].

Модель одна — `cursor-gpt55`; **усилие (effort) кодируется суффиксом
имени**: `(low)`/`(medium)`/`(high)`. Отдельного поля `reasoning` прокси
не требует и молча игнорирует. Прокси возвращает `model: "gpt-5.6-terra"` — это
и пишется в `raw_ocr.model`.

## Что наблюдалось

### gpt-5.6-terra ошибается на мелких цифрах order_number — лечится валидацией, не effort

На живых снимках `cursor-gpt55` примерно в **4%** случаев портит
`order_number`: теряет ведущую `1` в среднем блоке (`14584 → 4584`) или
читает её как букву (`14584 → I4584`). Это **систематический по типу**
сбой vision, который **выстреливает вероятностно** и **не лечится более
высоким effort** (high ошибался на тех же снимках). На пикселях видно, что
прав был прежний Kimi, а gpt-5.6-terra ронял цифру.

order_number — ключ идемпотентности `save_order`, поэтому сбой опасен.
Лечение — формат-валидация в [[app/validation.py]]:

- Формат eBay строгий: `^\d{2}-\d{5}-\d{5}$` (на всех распознанных
  номерах базы держится 100%). Известный сбой всегда ломает формат, значит
  ловится.
- **Стадия A** перечитывает снимок (`_ocr_suspect` + retry,
  `ocr_max_attempts=3`): ошибка вероятностная, повтор почти наверняка даёт
  валидный формат. Все попытки мимо → `OcrError` → снимок в `failed` на
  ручной разбор (кривой ключ в базу не пишем).
- **`save_order`** — формат-гард как блокер (`bad_order_number_format`):
  даже если кривой номер просочился, он не запишется.
- В системный промпт стадии A добавлена `IDENTIFIER_FORMATS_HINT` —
  просит перечитать ведущую цифру, но не подгонять под шаблон и не
  выдумывать.

Похожий узкий гард есть для `tracking_numbers` (UPS `1Z`+16=18; USPS `94…`
22 цифры) — `bad_tracking_reason`. Узко, чтобы не флагать легит-форматы
других перевозчиков.

### Strict JSON и `max_tokens` (стадия A)

`response_format: { type: "json_schema", json_schema: { …, strict: true } }`
работает и сильно повышает надёжность. Запас `llm_max_tokens ≈ 16000`,
чтобы длинные страницы (большой `visible_text`) влезали целиком и JSON не
обрывался.

### Картинки в запросе — base64 внутри тела

Картинки — data URL (`data:<mime>;base64,…`), потому что файлы локальные.
Скриншот ~1 МБ → пейлоад ~1.3 МБ. Один vision-вызов стадии A — порядка
10–20 секунд. **Таймауты не делать короткими**: `llm_timeout_s` 120с с
запасом.

### Tool-calling в стриме (стадия B)

`cursor-gpt55(high)` поддерживает tool-calling в стриме: дельты текста и
tool-вызовов приходят в одном SSE-потоке, формат идентичен OpenAI
(`delta.content`, `delta.tool_calls` с `index`). Аккумуляция tool_calls по
`index` — в [[app/llm.py]] (`stream_chat_step`). В одном шаге модель может
запросить несколько tool-вызовов сразу — исполняем параллельно под
семафором (см. [[параллельность tool-вызовов]]).

### Reasoning между шагами НЕ пробрасывается

Chat completions — stateless. В отличие от старого OpenRouter-сетапа,
`reasoning_details` обратно не шлём: прокси этого не требует, мультишаг
tool-loop корректно работает и так (проверено). Effort задаётся именем
модели на каждый вызов.

### Отмена стрима

Прерывание — `await stream.close()` на стороне SDK (в `stream_chat_step`
по `abort_check`); при дисконнекте клиента генератор получает
`CancelledError` и стрим закрывается. Проверено — без зависаний.

## Что отсюда уходит в SPEC, а что нет

Поведение системы (strict JSON, разный режим/усилие на A и B,
параллельность tool-вызовов, формат-валидация идентификаторов) — кандидаты
в `SPEC.yaml`. Здесь живут детали транспорта и эксплуатации: конкретный
прокси/модель, характерная латентность, формат-регэкспы, отсутствие цен.
Прежний этап (Kimi + OpenRouter + provider-routing) — пройден; оставлен в
истории git.

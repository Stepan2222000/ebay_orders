# Стадия B — известные проблемы и план правок

Документ собирает то, что мы выяснили во время большого прогона 178 снимков (8 мая, GPT-5.5 medium, ~36 параллельных save_order на step). Часть проблем фиксится сейчас, часть отложена.

## Контекст прогона

- 178 скриншотов на старте, 4 помечены `failed` (3 — другая валюта без USD, 1 — не страница заказа), 174 привязаны к 170 заказам.
- 6 шагов LLM, 36/34/42/35/25/2 tool_calls на step.
- `total cost = $1.92`, ~300K input tokens суммарно.
- Прогон занял ~25 минут.

Итог по данным — корректный: типизация полей 100%, реальные `item_title`/`item_number`, никаких галлюцинаций.

---

## Делаем сейчас

### 1. UI зависает, постоянно нужно перезагружать страницу

**Что не так.** В процессе активной сессии чат в браузере иногда «замирает»: pill «думает» висит, новые сообщения от агента не появляются, простого ответа можно не дождаться. Лечится только Cmd+R / hard reload.

В углу при этом висит постоянное предупреждение «1 Issue» от Next.js (hydration mismatch на `<html data-theme>` из-за `ThemeToggle`).

**Решение.**

- `suppressHydrationWarning={true}` на `<html>` в `app/layout.tsx` — штатный способ React сказать «атрибут меняется клиентом, не паникуй». Снимет «1 Issue» в углу и устранит главного подозреваемого в зависании React-state.
- Если после этого зависания всё равно повторяются — копаем глубже (auto-reconnect EventSource на фронте, проверка пула коннектов на бэке).

Главная цель захода — чтобы про Cmd+R можно было забыть.

---

### 2. Параллельный `save_order` — обязательно

**Что не так.** В `app/agent.py:run_agent_session` цикл по tool_calls идёт по очереди:

```python
for tc in final["tool_calls"]:
    yield {"type":"tool_start", ...}
    result = await execute_save_order(pool, args)   # ждём
    yield {"type":"tool_done", ...}
```

При 36 tool_calls × 0.5–2 сек каждая = 30–60 сек тишины между LLM-step'ами.

**Решение.** Запускать tool_calls батчем через `asyncio.gather` с `Semaphore(40)`. Каждый `execute_save_order` идёт в свой коннект пула. Время на 36 штук: ~5 сек вместо 30–60.

Параллельность безопасна: каждый save_order — отдельная транзакция, нет общих локов. При необходимости поднимем `pool.max_size` с 20 до 40 в `app/db.py`.

---

### 3. Счётчики прогресса агента

**Что не так.**

- Pill «✦ агент думает…» в шапке чата показывает только бинарное «работает/не работает» — нет числа.
- Сайдбар-счётчики (`0 ожидает / 0 идёт / 178 готово / 0 ошибка`) считают `screenshots.ocr_status`, не агента. После полного OCR они замораживаются.

**Решение.** Заменить pill на счётчик вида `Обработано 142 / 178 (4 ошибки)` в шапке чата. Виден только пока активна сессия, после finish пропадает. Если pending снимков нет (просто чат-вопрос) — счётчик не показывается, шапка чистая.

Сайдбар не трогаем — он отвечает за OCR.

---

## Делаем потом

### 4. Стриминг чата сделать моментальным

**Что не так.** Текст агента появляется кусками с заметными паузами: между токенами, между шагами LLM, между tool_calls. Длинные ответы выглядят «ступенчато».

**Решение (потом).** Переделать `/api/chat/stream` так, чтобы он отдавал только одно изменённое сообщение по `message_id` (а не всю историю), и фронт мерджил изменения в свой state по id вместо полной замены массива. Снизить throttle на бэке.

После этого текст будет печататься в реальном времени.

---

### 5. Нет индикатора «модель отвечает / выполняется N сохранений»

**Что не так.** Между шагами LLM или во время выполнения tool_calls UI не показывает, что именно происходит — пользователь видит «висящий» чат, хотя сервер реально работает.

**Решение (потом).** Тонкая subtle-строка под последним assistant-сообщением:

- идёт LLM-вызов → «модель отвечает…»
- идут save_order'ы → «выполняется N сохранений…»
- иначе — пусто

Источник — поле `phase` в `agent_run` (`thinking | tools | replying | idle`), воркер обновляет на границах, фронт читает из `/api/status/stream`.

---

### 6. Долгий первый step (~3 минуты на старте большого прогона)

**Что не так.** GPT-5.5 на старте получает огромный промпт: system 25K + полный observed для 178 снимков ≈ 25K токенов. Первый «mass call» с 36 tool_calls + reasoning занимает 2–3 минуты. Пока модель думает — в чате только «Вижу 178 снимков…», больше ничего.

**Решение (потом).** Структурно — ничего (чанкование снимков запрещено отдельно). Симптом смягчится после #5: появится строка «модель отвечает…», и пользователю будет ясно, что сервер не висит.

---

## Закрытые вопросы

- **Reasoning effort.** Оставляем `medium` всегда, без динамической логики «нет pending → low».
- **Счётчики в сайдбаре** — закрывается счётчиком из #3 в шапке чата.

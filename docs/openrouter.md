# Заметки по работе с OpenRouter

Это не часть `SPEC.yaml` и не часть `PLAN.md`. Это сжатый опыт от живых
прогонов через OpenRouter в этой системе. Сюда уходит то, что важно
знать перед тем как писать код, чтобы не наступать на те же грабли.
Что-то отсюда позже может перейти в SPEC, если станет осознанным
правилом системы; пока — наблюдения.

## Что используем

Через OpenRouter ходят обе стадии, но к разным моделям:

- **Стадия A** ([[Стадия A распознавание одного снимка]]) — vision-модель
  `moonshotai/kimi-k2.6`. Её задача — посмотреть на один скриншот и
  отдать строго структурированный JSON по нашей схеме.
- **Стадия B** ([[Стадия B сборка заказа]]) — `openai/gpt-5.5` в
  режиме tool-calling. Её задача — разговор с пользователем плюс
  вызовы инструментов из [[инструмент сохранения заказа]] и
  [[инструмент SQL]].

OpenRouter — прокси между нами и реальными хостерами. Запрос на одну и
ту же модель может уйти к разным провайдерам — это иногда важно
(см. ниже про «Inceptron»).

## Что наблюдалось

### Reasoning у разных моделей — разный режим

K2.6 поддерживает «внутренние мысли». По умолчанию они **включены**, и
для стадии A это сильно мешает: модель тратит десятки и сотни токенов
на размышления при простой транскрибации, эти токены съедают
`max_tokens`, и в strict-JSON это приводит к обрыву ответа посреди
структуры. Парсер падает.

Лечится отключением reasoning безусловно для каждого запроса стадии A.

GPT-5.5 наоборот: reasoning ей нужен, и для стадии B мы его явно
включаем (`reasoning.effort: medium`). Стадия B группирует снимки в
заказы, проверяет конфликты с базой и принимает решения — именно тот
профиль, где reasoning реально помогает. Конкретный effort — параметр
конфига, не правило системы.

Главное: каждой модели — свой режим reasoning, **не общая настройка
на всю систему**.

### Один из провайдеров OpenRouter зацикливался на длинных страницах

При первой реализации стадии A на нескольких пользовательских
скриншотах модель «застревала»: писала повторяющийся текст до тех пор,
пока не упрётся в лимит токенов, и ничего полезного не возвращала.
Запросы стабильно уходили к конкретному провайдеру (на момент
проблемы — **Inceptron**), на других провайдерах та же страница
распознавалась нормально.

Лечение — параметр `provider.ignore` на стороне OpenRouter. В чистом
OpenAI такой фичи нет.

Список «плохих» провайдеров может меняться. Стоит периодически
проверять реальное поведение и обновлять список. В коде этот параметр
живёт в одном месте, чтобы менять его быстро.

### Strict JSON и `max_tokens` (актуально для стадии A)

`response_format: { type: "json_schema", json_schema: { …, strict: true } }`
работает на K2.6 и сильно повышает надёжность. Но если ответ длинный
(большой `visible_text` от страницы с историей возвратов), он может
упереться в `max_tokens` и оборваться посередине JSON. Парсер падает.

Решение прагматичное: запас по токенам порядка 16000, чтобы длинные
страницы влезали целиком. На цене сказывается копейками.

### Картинки в запросе — base64 внутри тела

Картинки — data URL, потому что файлы локальные. Скриншот ~1 МБ
превращается в JSON-пейлоад ~1.3 МБ. Из этого:

- сам upload по TLS занимает заметное время (полсекунды — секунду);
- плюс работа модели — итого один vision-вызов 10–30 секунд для
  типичного скриншота eBay.

Практический вывод: **не делать таймауты короткими**. 30–60 секунд на
vision-вызов — нормально. 5 секунд — бессмысленно.

### Параллельность стадии A

5–10 одновременных запросов к OpenRouter — без 429. На наш профиль
работы (один пользователь, дроп пары десятков скриншотов разом) это
с большим запасом. Параллельность воркера стадии A можно ставить
смело.

### Параллельные tool-вызовы стадии B

Стадия B в одном LLM-step может попросить выполнить десяток-другой
действий сразу (см. [[параллельность tool-вызовов]]). На стороне
OpenRouter ничего особенного делать не надо — стрим корректно несёт
дельты разных tool-вызовов в одном потоке. Параллелизм исполнения —
на нашей стороне, ограниченный семафором, чтобы не упереться в число
свободных соединений с базой.

### Tool-calling в стриме

GPT-5.5 поддерживает tool-calling: агент в стриме чередует обычный
текст и вызов инструмента. На стороне OpenRouter это приходит как
дельты разного типа в одном SSE-стриме. На стороне фронта это
естественно поддерживает AI SDK v6 — отдельные парты для текста и
для tool-вызовов. Самим парсить формат не приходится.

### Стоимость

- Один скриншот стадии A — порядка $0.003–0.005.
- Стадия B на gpt-5.5 medium — большая пачка из ~180 снимков обходится
  в порядок $1–2 (живой замер). На цикле «5–20 заказов разом» — копейки.

В контракте системы цены не фигурируют, в `SPEC.yaml` их нет.

## Что отсюда уходит в SPEC, а что нет

В `SPEC.yaml` зафиксировано всё, что — **поведение системы**:
strict JSON, provider routing, разный режим reasoning на A и B,
параллельность tool-вызовов как принцип.

Здесь живут детали, которые **знать полезно**, но в контракт системы
они не попадают: конкретные числа, имя провайдера-исключения,
характерная латентность, цены. Если что-то отсюда становится правилом
системы — переезжает в SPEC, а здесь упоминается как пройденный этап.
